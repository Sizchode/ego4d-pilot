# Ego4D frozen-video-representation pilot

This repository evaluates whether latent-predictive video pretraining exposes
object-state-change information more effectively than supervised video and
image-only pretraining. The pilot uses the released Ego4D v1 OSCC/PNR splits,
published data loaders and metrics, and frozen backbone features.

The repository contains experiment code only. It does not contain Ego4D
videos, annotations, features, model checkpoints, credentials, environments,
or run artifacts.

## Experiment definition

The complete hypothesis, comparison matrix, endpoints, and interpretation
rules are documented in
[`reports/hypothesis_experiment.md`](reports/hypothesis_experiment.md).
The exact released data protocol is documented in
[`reports/data_protocol.md`](reports/data_protocol.md).

## Backbones

- `omnivore_video_swinl`: released Ego4D features and historical supervised
  video reference used by EgoPack.
- `vjepa2_vitl16`: frozen V-JEPA 2.1 ViT-L/16 video representation.
- `dinov2_vitl14`: frozen image-foundation-model control, evaluated on the
  center frame of every identical Ego4D temporal window.

Omnivore is retained as an in-domain historical reference; it is not treated
as the only modern video-foundation-model baseline.

## External code

Published loaders, task implementations, and metrics are reused from pinned
upstream repositories rather than reimplemented. See
[`reports/upstream_revisions.md`](reports/upstream_revisions.md).

Clone those repositories at the recorded revisions under `third_party/`.
That directory is intentionally excluded from version control.

## Storage configuration

Set the experiment root before running download scripts:

```bash
export EGO4D_PILOT_ROOT="$PWD"
export EGO4D_PILOT_SCRATCH="/path/to/scratch/ego4d-state-change"
export AWS_PROFILE_NAME="ego4d"
```

AWS credentials must be configured outside the repository. Never place them
in a configuration file committed to Git.

## Released split and manifests

Download only the official FHO annotations, then derive the video UID manifest
without changing the released split:

```bash
bash scripts/download_fho_annotations.sh

python scripts/build_oscc_pnr_video_uid_manifest.py \
  --annotation-dir "$EGO4D_PILOT_SCRATCH/data/ego4d/v1/annotations" \
  --output "$EGO4D_PILOT_SCRATCH/data/manifests/oscc_pnr_train_val_video_uids.txt" \
  --report "$EGO4D_PILOT_SCRATCH/data/manifests/oscc_pnr_split_report.json" \
  --manifest-splits train val
```

No example is reassigned, subsampled, relabeled, or generated by the manifest
builder.

## Published Omnivore reference

The Ego4D CLI version used in this pilot cannot apply UID filters to feature
datasets. Preview and download the complete released feature package:

```bash
EGO4D_VIDEO_DATASET=omnivore_video_swinl \
  bash scripts/preview_oscc_pnr_video_download.sh
bash scripts/download_ego4d_omnivore_video_features.sh
```

EgoPack then selects annotation-referenced videos through its published
dataset class.

## Frozen feature extraction

The adapters in `feature_models/` plug into the official Ego4D feature
extractor. Both video representations use 32-frame windows with stride 16.
Large videos are staged, processed, validated, and removed rather than kept as
a local copy of the complete Ego4D corpus.

The Slurm wrappers under `scripts/` resolve released video UIDs from the
validated manifest. Cluster resource requests are intentionally left to the
submission command because partitions and quotas are site-specific.

## Published task-head reproduction

The following command reproduces the single-task EgoPack Temporal Graph
reference. It is not a one-layer linear probe:

```bash
bash scripts/run_egopack_temporal_graph.sh oscc 65 omnivore_video_swinl
bash scripts/run_egopack_temporal_graph.sh pnr 65 omnivore_video_swinl
```

The paper seeds are `65`, `72`, and `97`. OSCC reports classification
accuracy; PNR reports mean absolute temporal localization error in seconds.

## Current scope

Feature extraction and the published EgoPack reference path are implemented.
The controlled identical-readout comparison is specified in the experiment
document and must be added from a published frozen-evaluation protocol before
it is reported as a result.
